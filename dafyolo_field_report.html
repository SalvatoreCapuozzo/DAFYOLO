01

Two systems living in one repo

Legacy DAFYOLO 6 merge strategies

client.py → client_updated.py → client_v2.py, and the matching server*.py trio. A client trains a full YOLO checkpoint per class-set on a remote (or local) node, uploads it over SSH, and the server merges incoming heads into a shared global model using a selectable strategy: FedHead, Stitch, TIES, FedAvg, FedProx, YOLO-Inc, YOLOPA-NeckHead. run_experiments.py automates a full strategy × scenario sweep over VOC classes.

Actively developed the longest — 11 of the repo's 12 commits touch this line of code. Now lives under legacy/ (moved there this pass — see §7).

fedyolo_system/ rewrite, verified on real data

A from-scratch redesign built around one structural argument: YOLOv8's detect head ends in a 1×1 conv where output channel c literally is class c's logit. Split the model along that seam — shared backbone/neck/box-head vs. one per-class parameter slice — and aggregation stops needing a merge heuristic at all: shared weights FedAvg normally, each class slice averages only across the nodes that actually own it. Ships both a sync (round-barrier) and async (staleness-discounted delta) server.

Added in the same commit as the analysis docs below. One complete real-dataset run beats its own centralized baseline on 2 of 20 classes and reaches 68% overall — see §4.

Reading the pattern

  • Every strategy collapses the same way. Local models land respectably (0.20–0.88 mAP50, YOLO-Inc's locals are genuinely strong at 0.6–0.87) but every merged global model falls to 0.001–0.165 — a 85–99% relative loss versus the average local score, regardless of which of the 6 strategies did the merging. That uniformity is itself informative: it points at something structural in how heads get merged or evaluated, not a strategy-specific bug.
  • FedHead and Stitch score identically in the 2026-04-30 run (0.042 / 0.064) — expected, since Stitch is documented as FedHead's conservative subset (only the final 1×1 layer touched either way) when run against the same client checkpoints; it's a useful sanity check that the two paths are wired correctly, not evidence either one works.
  • YOLO-Inc consistently scores highest (0.059–0.165) and also has the strongest local models feeding it — it isn't obviously a better merge strategy so much as a better-conditioned input.
  • YOLOPA-NeckHead is worse than random at 0.001 both times it was tested, despite feeding from the strongest local models of any run (0.64–0.88) — the neck-averaging step this strategy adds over FedHead is actively destructive here.
  • Run-to-run variance is large even for the same strategy. FedHead's EXTREME_NON_IID score moved from 0.042 → 0.005 between 2026-04-30 and 2026-05-04 with the same scenario definition — global mAP in this system is not a stable measurement, which matters when deciding whether a future fix actually helped.
03

Why the legacy global model collapses

Seven analysis documents in the repo root (ANALYSIS_AND_FIXES.md, FIXES_IMPLEMENTATION.md, ALTERNATIVE_STRATEGIES.md and four summaries of them) diagnose this exact collapse against client_updated.py / server_updated.py as they stood on 2026-05-04/05. Their headline numbers (4–17% global mAP against 30–87% local) match the logged experiments above closely enough to trust — but the code has moved since, in the very commit that added those documents to git. Two claims were spot-checked against the code as it exists today:

Claimed: duplicate trainer.train() call no longer present

Filed as the #1 critical, 1-minute fix — a second, redundant call to trainer.train() at client_updated.py:310, silently doubling every client's training time. The current file has exactly one trainer.train() call (client_updated.py:339). Either it was fixed in the same pass that produced these docs, or the line reference drifted — either way, don't spend the "1 hour, +100%" budget on this one.

Structural: no shared feature space still true, verified in code

None of the six merge strategies decompose per-class output channels the way fedyolo_system/fedyolo/model.py does. FedAvg, TIES and YOLO-Inc all blend backbone/neck weights trained on disjoint class sets — five separate feature extractors get averaged into one, at random-initialization scale where there's no pretrained anchor pulling them toward a shared basin. This is the one root cause every document, the logged numbers, and the architecture itself all agree on independently.

The remaining 10 claims across the seven documents (alpha-weight miscalculation, batch-norm momentum, validation-set class pollution, catastrophic forgetting, etc.) were not individually re-verified line-by-line for this report — treat their code-line references as of 2026-05-05 and re-check against current server_updated.py / client_updated.py before acting on any single one. The diagnosis (disjoint-class averaging breaks a from-scratch shared backbone) is corroborated independently by the numbers in §2 and is the one to act on first.

The absolute numbers are modest too, and a quarter of the per-class table is fake

new finding 0.303 / 0.446 mAP50 isn't just low relative to a centralized baseline — it's modest in absolute terms for a tuned detector, and part of why is a data problem hiding inside the per-class breakdown. Five of the "20 classes" — dictyocaulus, skrjabinema, toxocara, capillaria, giardia — report an identical per-class score in both the federated and centralized results (0.1747 / 0.2554 respectively) — suspicious because those numbers exactly equal each run's overall mAP50-95. Traced to source: counting every label file in the original /Users/salvatorecapuozzo/kfm_250423_subdataset/export (15,766 files), four of those five classes have zero annotated instances anywhere in the dataset, and the fifth (giardia) has exactly two. Ultralytics' own metrics code fills in the overall mean for classes it never evaluates, and fedyolo_system's summary writer reports that filler as if it were a measured score. It isn't — these classes have no data to learn from, full stop, regardless of federation strategy or config:

Verifying the gap, on this Mac, in minutes not hours

The point of this pass wasn't a bigger mAP number — it was checking whether the federated/centralized gap from the one real-data win (§4, 68% of centralized mAP50) holds up once the 5 unlearnable/near-empty classes are gone and the run is small enough to actually iterate on locally. Using the new balanced_fraction (§9) on the cleaned 15-class dataset: class-stratified 10% subset, sync mode, yolov8s@480 — same architecture as the July 4 run, cut from 20×5 to 5×2 epochs (10 vs. 100 epochs/node). Calibrated first (~110–115s/round at 1 local epoch) before committing to a full attempt. One complete run took ~35 minutes end to end (20 min federated + 15 min centralized) — small enough to run more than once in a sitting, which is the actual point of shrinking it.

Async verified — federated ≈ centralized

Highest raw mAP50 of any attempt on this dataset in both seeds, and seed 1's matched centralized run confirms it wasn't a fluke: federated (0.365) essentially matches its own centralized baseline (0.362) — 101%, the only run in this entire investigation where federation costs nothing measurable. A real reversal from the archival record (§4), where every async attempt on the messy, phantom-class dataset collapsed or underperformed — clean data looks like what async actually needed, not a different aggregation mechanism.

From scratch confirms pretrained matters

Federated and centralized collapse together (0.013 / 0.076) — at a 10-epoch/node budget, blank-weight YOLO genuinely can't learn this task, exactly as the framework's own "honest caveats" warn. This isolates the effect cleanly: pretrained: true (the current default) isn't a minor tuning knob here, it's load-bearing.

Pseudo-labeling actually turning on (D) landed statistically indistinguishable from the baseline that never had it (0.308 vs. 0.316) — inconclusive rather than a clear negative for the "shared macro-class info" hypothesis (three rounds of exposure, weight 0.5, may just be too little too late in a 5-round budget) — see below for what a more direct test of that idea would look like.

Open question: does per-class loss masking waste the shared "it's an egg" signal?

All 15 classes here are the same macro object — parasite eggs — just different species. Since a node's loss is masked to exactly zero for classes it doesn't own (client.py's class_weights), could that be throwing away a cross-species "there's an egg here" signal that would help every node, even ones that never see a given species?

Partly already answered by the architecture itself: fedyolo/model.py's shared/per-class split puts the backbone, neck, box-regression branch, DFL, and the two feature-mixing convs inside the classification branch (cv3.{i}.0, .1) in the shared, FedAvg'd-across-everyone bucket — only the final 1×1 per-class projection (cv3.{i}.2) is gated. So the entire visual representation, right up to the last layer, is already pooled across all four nodes regardless of species ownership. The genuine gap: loss masking zeroes a node's contribution everywhere for an unowned class, not just "don't suppress it" — so no node ever explicitly says "some egg, unknown species, is here," even though its own boxes are exactly that evidence in aggregate.

pseudo_label.py is the framework's existing answer to this gap — cross-round self-distillation from the previous global model for not-owned classes — which is why fixing its silently-broken start_round (config D, above) was the cheapest available test of the hypothesis. It came back inconclusive, not negative. A more direct test, if the hypothesis is worth pursuing further: add one new, class-agnostic output channel — binary "egg vs. background," never claiming which species — trained on the union of each node's owned-class boxes as positives. Because it never names a species, every node can supply full positive and negative supervision for it with no cross-node suppression risk (the exact problem loss-masking exists to prevent for the per-species channels). That's a model change, not a config flag — worth building only if a longer/cleaner pseudo-labeling test (more rounds, higher weight) shows the underlying idea has legs first.

Bigger picture

Every legacy strategy shares one root cause (§3): five backbones trained from random initialization on disjoint classes, averaged together with no shared feature space to land in. That argues for retiring the strategy-selector approach rather than continuing to add an eighth merge heuristic to it. fedyolo_system's class-decomposed head is a structural fix for exactly that failure mode — and on the cleaned real data, in async mode specifically, verified across two seeds, federation now costs nothing measurable (mAP50 101% of centralized). Sync mode lands lower and noisier (65-80%), and every async attempt in the archival record (§4) on the messier pre-cleanup dataset had collapsed — together that points at data quality as the actual cause of those earlier async failures, not the aggregation mechanism itself. Bigger model capacity (§5) raises the absolute ceiling (0.455 mAP50, the best of any attempt) without moving that ratio, and neither centralized nor federated reaches a genuinely satisfying number yet at this epoch budget — the target_map run's centralized phase (§4) was still climbing at epoch 25 of 25 without hitting 0.8. The remaining open items are narrow: ancylostoma's aggregation-damping (§5, confirmed via raw logits on the sync baseline) is visibly weaker in both async runs (AP50 0.50 and 0.55 — the best of any config, see the per-class grid in §5) than in sync/bigger-model runs (0.16-0.24) — worth confirming whether async's continuous, staleness-discounted updates are structurally why, rather than the round-barrier FedAvg sync uses; and whether giving async more rounds — the cheapest lever available, cheaper than a bigger model — closes the rest of the distance to "satisfying." Both are debugging and budget work, not a redesign.
